# Release assets for BoomBigNose ERP Harness AI

Repository: https://github.com/Boom-Vitt/boombignose-erp-harness-ai

`.github/workflows/boombignose-release.yml` builds the Wails window on GitHub-hosted runners:

- `BoomBigNose-windows-x64-setup.exe` from NSIS on `windows-latest`. The installer is unsigned. It installs `BoomBigNose.exe` (Windows GUI subsystem) and `bundle\` beside it: `node.exe`, `erp\server.js`, portable Postgres, `auth\auth.exe`, `postgrest\postgrest.exe`, and `ollama\ollama.exe` without the CUDA runners and without model weights. Compression is off. A silent install in CI checks those paths, then the smoke boots that directory.
- `BoomBigNose-macos-arm64.dmg` from `hdiutil` on `macos-14`, after `codesign --sign -` (ad-hoc, no purchased certificate). It contains `BoomBigNose` and `bundle/` (`node`, `erp/server.js`, portable Postgres, Auth, PostgREST, and the universal Ollama archive, including Metal). `hdiutil attach` is tried three times. A busy macOS runner can return `Resource temporarily unavailable` on the first attach. The mount check looks for the files. The smoke copies the mount to a writable directory, because a read-only UDZO image can drop the executable bit, and boots that copy.
- `BoomBigNose-linux-amd64.tar.gz` contains the Linux window binary named `BoomBigNose` and `bundle/`, including `bundle/ollama/bin/ollama` without the CUDA runners. It needs the system WebKitGTK 4.1 libraries. CI extracts the archive and smokes that tree.
- `BoomBigNose-linux-amd64.AppImage` wraps that same binary and copies `bundle/` to `usr/bin/bundle`. It also needs WebKitGTK 4.1. It does not bundle Docker. The Postgres data directory stays in the home directory. CI extracts the AppImage and smokes that tree. The tarball smoke and the AppImage smoke share one runner. The smoke waits until `127.0.0.1:3100`, `54329`, `54321`, `54323`, and `54324` can be bound again. A connect check misses `TIME_WAIT`, and PostgREST then exits with `Address in use`. Workflow run [40575390744](https://github.com/Boom-Vitt/boombignose-erp-harness-ai/actions/runs/40575390744) failed that way after the tarball smoke had already printed `signin ok`.
- `SHA256SUMS` covers those four files.

The workflow runs on push to `main` and on pull requests. Those runs build and upload Actions artifacts. They do not publish a release.

A desktop release is created as a draft, not published:

```
gh release create boombignose-vX.Y.Z --draft --target <commit on main> --title "BoomBigNose X.Y.Z" --notes-file notes.md
```

Creating that draft starts the workflow (`release` type `created`). The workflow marks an incomplete `boombignose-v*` release as a draft so `releases/latest` stays on the previous release. Installer jobs smoke the built files. The upload job runs only when the Windows, macOS, and Linux installer jobs succeeded and the gate asked for a build. It uploads the four installers and `SHA256SUMS`, downloads them again, and runs `sha256sum -c`. It also requests one byte of each asset URL with the workflow token. It leaves the release a draft and does not start the Pages workflow. After that check, `gh release edit <tag> --draft=false --latest` publishes it. Publishing starts the workflow again. When those five assets are already present, the gate skips the build and the upload job does not run. The download page is refreshed only after the published asset URLs return HTTP 200. Do not publish the draft before the upload. The workflow does not create the draft itself, and it does not replace assets on any other tag.

Tag `boombignose-v0.2.0` is the window only. It does not contain `bundle/`. Tag `boombignose-v0.2.1` contains Node, `server.js`, and portable Postgres. It does not contain Auth, PostgREST, or Ollama. Tag `boombignose-v0.3.0` is a non-prerelease from commit `0652c87`. Workflow run [40549096601](https://github.com/Boom-Vitt/boombignose-erp-harness-ai/actions/runs/40549096601) packed Node, `server.js`, portable Postgres, Auth v2.197.0, PostgREST v16.5, and Ollama v0.40.11, then printed `health ok`, `signup ok`, and `signin ok` against the extracted tar.gz, the extracted AppImage, the silent NSIS directory, and a writable copy of the mounted DMG. `sha256sum -c` matched the four uploaded files. Tag `boombignose-v0.3.1` does not contain `boombignose cutover apply`. Tag `boombignose-v1.0.0` is a non-prerelease of commit `e345808` and is the release `releases/latest` points at now. It contains that command. Workflow run [40571061823](https://github.com/Boom-Vitt/boombignose-erp-harness-ai/actions/runs/40571061823) uploaded its installers. The hashes are in `docs/GOALS.md`. The macOS bundle version and the Windows version resource on that tag are `1.0.0`. That tag was created before the draft-until-upload gate was on `main`, so the release was published at creation and the same run uploaded the files. In this tree those version resources are `1.1.0`. Tag `boombignose-v1.1.0` does not exist yet. Tag `boombignose-v0.1.1` is the older harness command (`boombignose check` and `boombignose cutover`). These builds are compiled in CI. They have not been click-tested on a physical machine. There is no paid code-signing certificate.

The window refuses cloud model keys. When `bundle/node` and `bundle/erp/server.js` are present it starts that server. Otherwise, when `127.0.0.1:3100` is closed and it finds a checkout, it runs `node scripts/local/stack.mjs serve --port 3100`.

No code-signing certificate is required for this step.
