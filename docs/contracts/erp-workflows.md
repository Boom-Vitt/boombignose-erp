# Contract v1: services pilot

Coordinator is the sole schema/types/contract writer. All amounts are integer satang, bounded to 0..9007199254740991 (positive for receipts). decimal THB payment input is parsed exactly. A DB transaction owns settlement, allocation, invoice balance/status, command result and trusted audit. Authorization and tenant-qualified relationships apply even through direct Supabase API calls.

Roles: owner/admin may verify or reject payments, manage invitations/settings/accounting/templates/subscriptions, convert quotes and delete protected business records. Members may read their memberships' business data and do ordinary permitted CRUD. App queries MUST also filter the server-derived active org; membership RLS covers all memberships and does not choose the active organization.

`submit_payment_claim(p_token,p_invoice_id,p_amount_satang,p_reference,p_key) -> claim UUID`: service-role execution only, called from public server action after validation. DB resolves enabled token to client/org under a lock. Invoice must belong to that client/org and be sent/overdue/partial. Positive reported amount cannot exceed verified open balance. At most one pending report per invoice. No receipt, allocation or status change. Same key/request retries return the original claim; changed request conflicts. Pending amount/reference are customer assertions, not settlement evidence.

`review_payment_claim(p_org_id,p_claim_id,p_amount_satang,p_reference,p_key,p_decision) -> receipt UUID (verified) or claim UUID (rejected)`: authenticated only, owner/admin checked inside DB. Key scoped to org; same request returns durable result, different request conflicts. Invoice then claim locking serializes competing settlement. Positive verified amount must not exceed claim/open balance. Verification reference must identify actual receipt evidence. Reject uses amount 0 plus reason. Partial/full receipts are allocated to that invoice atomically. Draft/cancelled/fully paid invoices and overpayment fail. Allocation UI is currently one receipt to one invoice. Manual unverified `recordPayment` is contained; public reports must enter the queue.

All old receipts stay `legacy_unverified`. They are visible for reconciliation and excluded from verified cash/balances. No migration silently certifies or deletes them. Existing stored paid flags may conflict with verified balance; that discrepancy is a release blocker needing an authorized reconciliation command. Existing violations of tenant FKs fail the upgrade. NOT VALID amount checks enforce new writes but require legacy preflight/validation before release.

Next contract batches (not implemented by this document): provision_workspace (authenticated name/key -> org), convert_accepted_quote (org/quote/key -> source-linked project/milestone/invoice), enqueue_reminders (org/stable keys -> reminder/event), generate_subscription_occurrence (subscription/scheduled date -> invoice+advance). Their consumers wait for coordinator migrations and typed signatures. Issued snapshots, credits/withholding, manual bank settlement and correction controls require explicit acceptance fixtures; no statutory accounting claim.

Release evidence must include fresh replay, upgrade preflight, direct API matrix, cross-org links, retries/concurrency, fault injection, active-org switching and real accountant-reviewed customer workflows. No deploy/push/main merge, production migration, real import or outreach is included.

Pilot review repairs: every accepted alias key has a durable portal_claim_requests entry; caller-authored audits cannot impersonate payment events/actors. Pending claims prevent customer reassignment and review revalidates client binding. Verified settlement/pending claim prevents line changes; unverified line mutation and exact header recompute are atomic DB triggers. Fully settled headers remain paid. Client retries retain commands across transport failures; changing inputs/decision creates a new command.

Frozen next-batch signatures (consumers may implement against these; coordinator supplies SQL/types):
- provision_workspace(p_name text,p_key uuid) -> org UUID; authenticated own actor, nonempty name<=100, same actor/key name retry durable, changed name conflict.
- accept_workspace_invitation(p_token text) -> org UUID; authenticated intended email, row lock, pending/nonexpired; own accepted retry returns org; atomic membership+acceptance, no role upgrade of existing member.
- convert_accepted_quote(p_org_id uuid,p_quote_id uuid,p_key uuid) -> invoice UUID; owner/admin, accepted/nonexpired quote, creates linked project if absent and a delivery milestone, one complete draft invoice+lines; durable source link retries, converted quote frozen. Display number separate from command identity.
- enqueue_reminders(p_org_id uuid,p_specs jsonb) -> JSON {remindersUpserted,eventsQueued}; owner/admin or service-role cron, stable aggregate/date key; atomically reminder+event and repair legacy orphan event. Event version1, stable event UUID, org+source identity, retries at least once.
- generate_subscription_occurrence(p_org_id uuid,p_subscription_id uuid,p_occurrence date) -> invoice UUID; owner/admin or service-role cron; precise scheduled occurrence key (subscription ID/date), lock subscription, one invoice and advance next_run in one transaction. Weekly+7days; monthly/quarterly/yearly anchored to start-day with month-end clamping; delayed run bills scheduled date, one occurrence per invocation (catch-up through repeated invocations), period result survives rename.

No consumer writes migrations or regenerates types. Missing-contract behavior is a dependency, not permission to use multi-call settlement/billing writes.

Automation schema batch: recurrence creates a **draft** invoice with one full priced line and due date scheduled occurrence+15 days. Display number is SUB-<full UUID>-YYYYMMDD; subscription/date identity survives rename. Billed customer/project/cadence are frozen; only the transaction advances next_run/last_generated. Staff issue separately. Reminders and outbox writes are command-only for authenticated callers; service delivery claims a bounded 30..600 second lease with SKIP LOCKED and must acknowledge the exact unexpired token. Failed delivery backs off, same event ID is reused after lease expiry. This is at-least-once delivery; external receivers must deduplicate event UUID. No external sender is configured by this change.

Frozen finance batch: submit_internal_payment_claim(p_org_id uuid,p_invoice_id uuid,p_amount_satang bigint,p_reference text,p_key uuid)->uuid: staff pending assertion with durable retry, no settlement. reconcile_legacy_payment(p_org_id uuid,p_legacy_payment_id uuid,p_amount_satang bigint,p_reference text,p_key uuid)->uuid: staff actual bank evidence creates a new verified allocation, retains original record linked to the result, same-key retries return durable result. Original amount is not overwritten; reconciliation is not an automatic certification. Payment-date/method and issue/correction snapshots need the subsequent explicit contract batch.
